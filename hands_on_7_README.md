## Task 1: Setup Alembic and Create Baseline Migration

### Step 1 — Install Alembic
```bash
pip install alembic psycopg2-binary
```

### Step 2 — Initialise Alembic
```bash
alembic init migrations
```

### Step 3 — Edit alembic.ini
Open `alembic.ini` and update the database URL:
```
sqlalchemy.url = postgresql+psycopg2://postgres:your_password@localhost/college_db_orm
```
For MySQL:
```
sqlalchemy.url = mysql+mysqlconnector://root:your_password@localhost/college_db_orm
```

### Step 4 — Replace env.py
Replace the contents of `migrations/env.py` with the provided `env.py` file.
It imports your `Base` from `models.py` so Alembic can detect schema changes.

### Step 5 — Generate Initial Migration
```bash
alembic revision --autogenerate -m "initial schema"
```
Open the generated file in `migrations/versions/` and confirm:
- `upgrade()` contains `op.create_table(...)` for all 5 tables
- `downgrade()` contains `op.drop_table(...)` for all 5 tables

### Step 6 — Apply Migration
```bash
alembic upgrade head
```

### Step 7 — Verify
```bash
alembic current
```
Expected output: `<revision_hash> (head)`

Check in your SQL client:
```sql
-- PostgreSQL
\dt
SELECT * FROM alembic_version;

-- MySQL
SHOW TABLES;
SELECT * FROM alembic_version;
```
Expected: 6 tables (5 schema tables + alembic_version)

## Task 2: Add Incremental Migrations

### Step 1 — is_active column already added in models.py
The `Student` model now has:
```python
is_active = Column(Boolean, default=True)
```

### Step 2 — Generate migration for is_active
```bash
alembic revision --autogenerate -m "add is_active to students"
```
Inspect the generated file — confirm:
- `upgrade()` → `op.add_column('students', sa.Column('is_active', sa.Boolean(), server_default='true'))`
- `downgrade()` → `op.drop_column('students', 'is_active')`

### Step 3 — Apply migration
```bash
alembic upgrade head
```
Verify in SQL client:
```sql
-- PostgreSQL
\d students

-- MySQL
DESCRIBE students;
```
Expected: `is_active` column appears with default TRUE.

### Step 4 — CourseSchedule table already added in models.py
The `CourseSchedule` model is defined with:
- `schedule_id`, `course_id` (FK), `day_of_week`, `start_time`, `end_time`

### Step 5 — Generate migration for CourseSchedule
```bash
alembic revision --autogenerate -m "add course schedules table"
```
Inspect — confirm `upgrade()` creates `course_schedules` table and `downgrade()` drops it.

### Step 6 — Apply migration
```bash
alembic upgrade head
```

### Step 7 — View full migration history
```bash
alembic history --verbose
```
Expected output (3 revisions):
```
<rev3> (head) -> add course schedules table
<rev2> -> <rev3>  add is_active to students
<base> -> <rev2>  initial schema
```

## Task 3: Rollback and Recovery

### Step 1 — Check current revision
```bash
alembic current
```

### Step 2 — Roll back one step (drops is_active... wait, order matters)
```bash
alembic downgrade -1
```
Verify `course_schedules` table is dropped (last migration undone).

### Step 3 — Roll back one more step
```bash
alembic downgrade -1
```
Verify `is_active` column is dropped from students.

### Step 4 — Roll back to base (removes everything)
```bash
alembic downgrade base
```
Verify all 5 tables are dropped and `alembic_version` is empty.

### Step 5 — Re-apply all migrations
```bash
alembic upgrade head
```
Verify you are back to the full schema:
```bash
alembic current
```
Expected: points to head revision hash (same as after Task 2).

## Quick Reference — Alembic Commands

| Command | What it does |
|---|---|
| `alembic init migrations` | Initialise migrations folder |
| `alembic revision --autogenerate -m "msg"` | Generate migration from model diff |
| `alembic upgrade head` | Apply all pending migrations |
| `alembic downgrade -1` | Roll back one revision |
| `alembic downgrade base` | Roll back all migrations |
| `alembic current` | Show currently applied revision |
| `alembic history --verbose` | Show full migration chain |

---

> **Important:** Always inspect autogenerated migration files before applying.
> Alembic may miss column renames — edit the file manually if needed.
> Never run `downgrade` on a production database without a backup.
